# Агентские маршруты и handoff

## Диспетчер

Главный агент читает `AGENTS.md` и `state.md`, затем по активному run выбирает маршрут из `config/routes.json`. На каждом гейте он отвечает за конкретный артефакт, координацию независимого ревью, пользовательскую карточку и запись результата.

| Роль | Гейты | Ответственность |
|---|---|---|
| **Orchestrator** | G0–G11 | Порядок, память, пользовательские решения, ограничения, статусы |
| **Trend Scout** | G1 | Сигналы, источники, дедупликация, география, датировки |
| **Concept Designer** | G2 | Три идеи с различными игровыми выборами и ясным обещанием |
| **Prototype Builder** | G3–G5 | A0 и изолированные мутации; настоящий играбельный цикл |
| **UX / Art Director** | G2, G3, G6 | Понятность, формы, интерфейс, три сравнимых стиля |
| **Distribution Designer** | G0, G2, G5, G7, G10, G11 | Канал, распространение, обещание и реальный путь получателя |
| **Systems Designer** | G8–G9 | Прогрессия, экономика, взаимосвязи и полный GDD |
| **Experiment Analyst** | G2, G5, G10 | Тест-план, сопоставимость, наблюдаемые результаты, ограничения |
| **Release Coordinator** | G11 | Пакет публикации и требования конкретной платформы |

Одна модель может последовательно исполнять разные рабочие роли. На обязательных контрольных точках назначаются **отдельные субагенты** по `docs/REVIEW_PROTOCOL.md`; автор не ревьюит собственную работу как независимый эксперт.

## Маршрут исследования

1. Зафиксировать G0: аудитория, география, платформа, тип сессии, канал, бюджет.
2. Собрать сырые evidence и ссылки на оригиналы, затем нормализовать signals.
3. Объединить перепосты в clusters; не выводить органику из просмотров и рейтингов.
4. Показать три территории с контргипотезами, сравнимыми аналогами и дешёвыми тестами.
5. Независимые линзы G1 → правки → повторная проверка → карточка пользователя.

## Маршрут дизайна и производства прототипа

1. G2: три концепта, единый формат. Раннюю понятность пометить `pass/fail/blocked/not_run`.
2. G3: собственно игровой прототип A0 с завершённым циклом; сохранить исходный коммит или отдельный неизменённый build.
3. G4: independent variations с **одним новым правилом на ветку**. Каждая записывает новый выбор игрока.
4. G5: наблюдать людей, сравнивать с A0, фиксировать откат и причины; не симулировать игроков языковой моделью.
5. G6–G9: стиль, причина делиться, минимум прогрессии и окончательный дизайн из принятых решений.

## Маршрут среды

При запуске прототипирования сначала проверить, что реально доступно: Git, Python, браузер/Playwright, Godot, удалённый рабочий стол, модель генерации визуальных материалов, тестовые устройства, публикация. Проверка успешности: `pass/fail/blocked/not_run`. Нельзя объявлять подключённый инструмент работающим только потому, что он упоминался в предыдущем проекте.

Если Godot недоступен, агент может предложить локальный HTML/JS greybox с честным указанием, какие ощущения и ограничения им можно проверить. Если обещанное действие зависит от специализированной физики или мультиплеера, упрощённый прототип считается ограниченной проверкой и это фиксируется для пользователя.

## Handoff после полного дизайна

После утверждения G9 создаётся пакет: `design.md`/`GDD.md`, принятые правила, обоснованные отклонения, прототип, версии, референсы с правами, критерии приёмки, гипотезы, ограничения, `state.md` и сводка user decisions.

Опциональный адаптер к существующей [Game Factory](HANDOFF_GAME_FACTORY.md) описан отдельно. Наличие второго репозитория, его инструментов и внутренних гейтов проверяется при передаче.

## Работа волнами

В конце каждой волны фиксировать: выполнено; подтверждено; отвергнуто; изменено; тесты; текущая версия; блокеры; следующий конкретный шаг. При возобновлении новая сессия начинает с этих данных. Никаких скрытых продолжений через пользовательский approval gate.
