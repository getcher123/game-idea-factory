# Следующий этап: пилотный прогон G0→G1→G2

**Статус:** runbook готов; пилот пока не запускался. Цель пилота — проверить работу агентских маршрутов, правдивость данных, независимое ревью и утверждения пользователя до затрат на полноценное производство игры.

## 1. Условия и границы

- Стартовать **только с G0**; ранее не выбраны ни платформа, ни аудитория, ни отдельная игра.
- Первое исследование G1 проводит реальные открытые поиски под утверждённую рамку, а не выдаёт старый отчёт за свежий мониторинг.
- На G1 два разных субагента независимо проверяют `evidence` и `market_skeptic`. При недоступности — `BLOCKED`.
- G2 приносит три сравнимых концепта с наглядными карточками и проверкой понятности. Если внешней аудитории для теста пока нет — честное `not_run`.
- Остановиться на явном утверждении концепта G2. Играбельное A0 — следующая волна после пилота.

## 2. Предполетная проверка

1. Прочитать `AGENTS.md`, `state.md`, маршруты и регламент ревью.
2. Проверить фактическую доступность GitHub, поиска, браузера и возможности запустить независимых субагентов.
3. Выполнить `python3 -m unittest discover -s tests -v` и `python3 tools/pipeline.py check-repo`.
4. Отдельно проверить на будущее Godot/Remote Desktop/генерацию изображений; `not_run` допустим, если инструмент не нужен на текущем гейте.
5. Для любой недоступной функции зафиксировать конкретный блокер и ограниченный доступный альтернативный маршрут.

## 3. Создать прогон

```bash
python3 tools/pipeline.py init --run pilot-20261111-01 --through G2
python3 tools/pipeline.py status --run pilot-20261111-01
python3 tools/pipeline.py audit --run pilot-20261111-01
```

`init` создаёт рабочую папку и `run.json`. Он не выбирает за пользователя направление и не делает сетевых запросов.

## 4. G0: согласование рамки

Показать **наглядные варианты** платформы (например, браузер/Android/Roblox) и аудитории с разницей в формате сеанса, возможностях производства, канале и проверках. Рекомендация агента допустима, но это гипотеза до выбора пользователя.

После подготовки окончательной карточки зарегистрировать manifest и зафиксировать версию пакета:

```bash
python3 tools/pipeline.py propose --run pilot-20261111-01 --manifest artifacts/G0-v1/proposal.json
```

Команда ожидает manifest внутри run; агент сначала создаёт конкретный материал и перечисляет его файлы, авторов и варианты выбора в `proposal.json` по схеме. После регистрации показывает пользователю эту зафиксированную версию и **ожидает фактического ответа пользователя**. Хэш хранится в служебной записи пакета; пользователю достаточно понятного номера версии и наглядных вариантов. Нельзя вводить фиктивный ответ ради зелёного статуса. После настоящего ответа используется `approve` с хэшем показанного пакета, ID выбранного варианта, буквальной цитатой и ссылкой на сообщение (см. `docs/APPROVALS.md` и `docs/CLI.md`).

## 5. G1: исследование и ревью

1. Собрать реальные открытые свидетельства и нормализовать их в JSONL.
2. Создать `clusters.json` и `opportunities.json` с тремя территориями.
3. Выполнить:

   ```bash
   python3 tools/pipeline.py validate-research --run pilot-20261111-01
   ```

4. Создать manifest G1 со всеми четырьмя файлами исследования и карточками, зарегистрировать через `propose`, предъявить пакет двум **отдельным** субагентам: `evidence` и `market_skeptic`.
5. Сохранить каждый отзыв в `reviews/` и внести через `review`. После изменения материалов повторить `propose` и получить новые независимые ревью нового хэша; прежние отзывы сохраняются в истории и не разблокируют новую версию.
6. Показать пользователю три территории и перейти к G2 **только после его явного выбора**.

## 6. G2: три игровых концепта

- Одинаковая форма: что игрок делает → какой выбор → последствия → успех/провал → повтор → повод поделиться.
- Три разных механических варианта. Добавить визуальный эскиз или небольшой интерактивный сценарий, если доступен.
- Сравнить близкие аналоги; назвать риск копирования и отличающее правило.
- Проверить понимание несколькими внешними людьми при доступности. Иначе отметить `not_run`, не выдумывать поведенческие данные.
- Показать человеку **конкретное** решение и остановиться на нём.

## 7. Приёмка пилота

Пилот пройден только при наличии:

- подлинного одобрения G0;
- реальных записей evidence/signals, трёх территорий, ссылок и контрсвидетельств;
- двух независимых положительных ревью G1 по разным линзам, исправленных блокеров;
- подлинного одобрения выбранной территории G1;
- трёх сравнимых концептов и наглядной карточки G2;
- подлинного решения пользователя по концепту **или честной остановки в ожидании этого решения**;
- машинного аудита без выдуманных или просроченных утверждений.

В финальном отчёте пилота разделить: **выполнено**, **blocked**, **not_run**, **решения пользователя**, **следующий возможный gate G3**. Если пользователь ещё не утвердил G2, стадия остаётся G2. После его утверждения run имеет `complete` на G2. Команда `extend --through G9` применяется только после явного разрешения продолжить разработку и переводит run в G3.

## 8. Возобновление после перерыва

```bash
python3 tools/pipeline.py status --run pilot-20261111-01
python3 tools/pipeline.py audit --run pilot-20261111-01
```

Прочитать артефакты текущего gate и записи предыдущих решений; продолжить с него. Не восстанавливать устаревший выбор из пересказа разговора, если `run.json` содержит иной статус. После каждой волны обновить `state.md` как обзор активного прогона и новых ограничений.
