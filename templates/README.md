# Шаблоны артефактов одного прогона

Шаблоны задают **вопросы и поля**, а не готовые выводы. Копируй нужный шаблон в `runs/<run_id>/artifacts/`, заполняй из действительных решений, файлов и наблюдений. Не создавай для текущего прогона заранее выбранную игру. `run.json`, решения и отчёты ревью существуют отдельно от этих человекочитаемых материалов.

| Гейт / задача | Шаблон | Что становится видимым |
|---|---|---|
| G0 | [`g0-brief.md`](g0-brief.md) | Явные альтернативы рамки проекта |
| G1 | [`g1-signal.md`](g1-signal.md) | Связь реального сигнала с игровым действием |
| G2 | [`g2-concept.md`](g2-concept.md) | Три принципиально разные игровые идеи |
| Любое утверждение | [`approval-card.md`](approval-card.md) | Один выбор пользователя и его последствия |
| G4 | [`g4-single-mutation.md`](g4-single-mutation.md) | Одно изменённое правило относительно A0 |
| G2/G5/G10 и проверки | [`experiment-plan.md`](experiment-plan.md), [`experiment-results.md`](experiment-results.md) | План до наблюдения, реальные факты после |
| G9 | [`g9-design-handoff.md`](g9-design-handoff.md) | Полный дизайн первой версии и приёмка |
| Обязательные ревью | [`review-report.md`](review-report.md) | Наблюдаемые замечания независимого проверяющего |
| Любой G0–G11 | [`proposal-manifest.md`](proposal-manifest.md) | Как собрать полный проверяемый JSON manifest |

## Сборка предложения к утверждению

1. Заполни профильный Markdown, связанные JSON/JSONL, визуальные материалы, реально существующие билды, записи и результаты. Все материалы должны находиться в текущем `runs/<run_id>/`. Если пользовательская карточка входит в manifest, заверши её **без итогового SHA и заключений будущих ревью**: эти значения показываются отдельно после регистрации, чтобы не менять содержимое уже хэшированного файла.
2. Создай `artifacts/<gate>-proposal.json` по [`proposal-manifest.md`](proposal-manifest.md): `gate` должен быть текущим, `author_ids` — реальные уникальные ID авторов, `files` — **все** существенные относительные пути внутри прогона (исследование, варианты, исходники/билды прототипов, карточки, план и результаты), `summary` — точный смысл выбора, `options` — имеющиеся ID и подписи, `is_synthetic` — строго `false` только для реальной работы. Не включай сам manifest в `files`.
3. Убедись, что каждый путь существует и файлы не изменятся до проверки. Запусти `python3 tools/pipeline.py propose --run <run_id> --manifest artifacts/<gate>-proposal.json`. Общий SHA-256 связывает manifest и **содержимое каждого указанного файла**, а не один Markdown.
4. На G1/G3/G5/G9/G11 передай **зарегистрированный SHA** независимым ревьюерам; в `reviews/` сохраняй валидные JSON-отчёты по `schemas/review.schema.json` и регистрируй через `review --file`. При исправлении любого файла или manifest повтори `propose`, получи новый SHA и повтори ревью. Markdown здесь служит инструкцией по заполнению отчёта.
5. Покажи [`approval-card.md`](approval-card.md) пользователю **после** ревью, не регистрируя повторно ту же неизменённую версию. Реальный ответ пользователя с точной цитатой и ссылкой на сообщение требуется после показа связанного с SHA материала. Клики в локальном HTML — предварительный выбор.

В репозитории есть [`examples/proposal-synthetic.json`](../examples/proposal-synthetic.json) — **полный, но специально синтетический** пример схемы. Он не является фактом исследования и запрещён к использованию как предложение реального прогона. Отсутствующие исследования, тесты, ревью и согласования называй `not_run`, `unknown` или `BLOCKED` согласно протоколу, не придумывай значения.

**Граница пилота:** прогон `init --through G2` заканчивается на G2. Для G3–G9 требуется отдельная команда `extend --through G9` после явного пользовательского разрешения с дословной цитатой и `message_ref`; дальше G9 автоматического перехода также нет.
